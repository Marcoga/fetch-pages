Multi-Agent Strategy: The Fetch Ecosystem

Date: February 20, 2026

Status: Proposal — v2 (Shared Context & Privacy)

1. Executive Summary

The current setup relies on a single "Fetch" agent to manage disparate domains: high-stakes trading (i360), physical performance (Climbing Lab), personal habits (The Protocol), and infrastructure (SysAdmin). This monolithic approach creates risks of context pollution, tool misuse, and reduced specialized performance.

This proposal recommends transitioning to a Federated Agent Model, where dedicated agents handle specific domains, routed via context-aware bindings (primarily WhatsApp Groups).

v2 Addition: This revision introduces a Privacy & Identity Layer to support secondary users (starting with Giselle) who need to interact with shared agents while being strictly isolated from personal domains.

2. Current vs. Proposed Architecture

Current State (Monolithic)

  • Single Agent: "Fetch" handles everything.
  • Shared Context: Trading logs mix with climbing beta and server alerts.
  • Security Risk: A hallucination in a climbing chat could trigger a SysAdmin tool.
  • Prompt Dilution: System prompt must cover too many domains, reducing specific efficacy.

Proposed State (Federated + Identity-Aware)

  • Agent 1: Fetch (Main) — Habits, Journaling, General Life (The Protocol). Gatekeeper
  • Agent 2: i360 (Trader) — Market analysis, Position management. Personal
  • Agent 3: Climbing Lab — Vision analysis, Training logs. Shared
  • Agent 4: SysAdmin — Infrastructure, Cloudflare, Nginx. Personal
  • Agent 5: Travel Planner — Trips, itineraries, bookings. Shared
  • Agent 6: Household — Groceries, chores, shared logistics. Shared

3. Agent Specialization & Isolation

Why Isolate?

  • Context Purity: The i360 agent's memory only contains market data, not climbing shoe sizes. This reduces hallucinations and improves financial reasoning.
  • Tool Safety: The SysAdmin agent is the only one with exec or ssh access. The General agent cannot accidentally delete files.
  • Model Optimization:
    • Trading: High-reasoning model (e.g., Claude Opus).
    • Climbing: Vision-capable model (e.g., GPT-4o).
    • General: Fast, conversational model.
  • Privacy Boundary: Shared agents never load personal memory files. Personal agents never accept messages from secondary users.

5. Shared Context & Privacy Layer

This section defines how the agent ecosystem handles multi-user access while maintaining strict privacy boundaries. The first secondary user is Giselle (Marco's girlfriend), but the architecture is designed to be generalizable.

5.1 Design Principles

  • Deny by Default: No agent shares personal information unless the domain is explicitly classified as Shared.
  • Identity at the Edge: The sender's phone number is resolved to an identity before any agent logic runs. This is not an afterthought — it's the first routing decision.
  • Gatekeeper Pattern: Fetch (Main) is the only agent that receives DMs from all users. It decides what to answer, what to delegate, and what to refuse.
  • No Cross-Contamination: Shared agents have their own memory stores. They never read from MEMORY.md, memory/, or any personal workspace file.

5.2 Domain Classification

🟢 Shared Domains (Both Users)

Agents in these domains accept messages from Marco AND Giselle. Memory is jointly visible.

  • Climbing Lab — Training sessions, beta spray, gym check-ins. Both climb together.
  • Travel Planner — Trip planning, flight/hotel bookings, itineraries. Trips are shared.
  • Household — Grocery lists, chores, shared calendar events, apartment logistics.

🔴 Personal Domains (Marco Only)

Agents in these domains reject or ignore messages from any sender other than Marco. No exceptions.

  • i360 (Trader) — All financial data: positions, P&L, strategy, market analysis.
  • Private Finances — Bank accounts, investments, tax documents.
  • SysAdmin — Server infrastructure, SSH keys, system configuration.
  • Personal Files — Journal (MEMORY.md), private notes, work documents.
  • The Protocol — Personal habits, health metrics, private journaling.

5.4 The Gatekeeper: Fetch (Main)

Fetch (Main) is the central router and privacy enforcer. When Giselle sends a DM, Fetch (Main) operates in restricted mode:

5.5 Routing Rules for Giselle's Number

These rules are evaluated in order. The first match wins.

Rule Chain

  1. Personal Group → BLOCK: If Giselle's number appears in a Personal domain group (i360, SysAdmin), the agent does not respond. The group should not include her, but this is a safety net.
  2. Shared Group → ALLOW: If Giselle messages in a Shared domain group (Climbing Lab, Travel, Household), the agent responds normally with full shared context.
  3. DM → Fetch (Main) Restricted Mode: If Giselle DMs the bot directly, Fetch (Main) activates with a restricted persona:
    • Loads SOUL-shared.md (a persona file without personal details).
    • Does NOT load MEMORY.md or memory/*.md.
    • Can delegate to Shared agents only.
    • Cannot invoke tools: exec, ssh, read (on personal paths), write (on personal paths).
  4. Unknown Number → IGNORE: No response to unrecognized senders.

5.8 Persona Files

Each agent loads a persona (SOUL.md) appropriate to the user and domain:

Persona Loading Strategy

  • SOUL.md — Full persona with personal context. Loaded by Fetch (Main) when Marco messages. Contains preferences, private notes, personality calibration.
  • SOUL-shared.md — A stripped-down persona for shared contexts. Loaded when Giselle (or any secondary user) interacts with Fetch (Main) via DM. Friendly, helpful, but contains zero personal information about Marco.
  • Agent-specific SOUL files — Shared agents (Climbing, Travel, Household) use their own domain-specific SOUL files that contain no personal data by design. Safe for all authorized users.

# SOUL-shared.md (Example)

You are Fetch, a friendly AI assistant for the household.

You help with:
- Shared planning (travel, climbing, household)
- General questions and information
- Coordinating between Marco and Giselle

You DO NOT:
- Share personal information about any user
- Access financial data, work files, or private journals
- Run system commands or access infrastructure
- Reveal the existence of personal domains to secondary users

8. Security Considerations

🔒 Threat Model

Threat Mitigation
Giselle asks personal agent directly Identity check blocks at binding level. Agent won't activate.
Prompt injection via shared group Shared agents have no access to personal memory or tools. Nothing to leak.
Social engineering via DM ("Marco said to tell me his trades") Gatekeeper (Fetch Main) never reveals personal data regardless of claimed context.
Phone number spoofing WhatsApp E2E encryption makes spoofing impractical. Accepted risk.
Shared agent leaks personal data from memory Shared agents use isolated workspaces. No file path overlap with personal stores.
Agent-to-agent delegation leaks Fetch (Main) in restricted mode cannot delegate to personal agents. Delegation chain respects caller identity.

9. Implementation Roadmap

  1. Phase 1: Identity Layer
    • Add users section to openclaw.json.
    • Implement sender→identity resolution in the binding engine.
    • Create SOUL-shared.md persona file.
  2. Phase 2: Shared Agent Workspaces
    • Create workspaces: workspace-climbing, workspace-travel, workspace-household.
    • Set up shared memory directories with appropriate permissions.
    • Write domain-specific SOUL files for each agent.
  3. Phase 3: WhatsApp Groups
    • Create shared groups (Climbing Lab, Travel, Household) and add both Marco and Giselle.
    • Create personal groups (i360, SysAdmin) with Marco only.
    • Add the bot to all groups and capture Group IDs.
  4. Phase 4: Gatekeeper Logic
    • Implement restricted mode for Fetch (Main) when secondary users DM.
    • Test delegation chain: Giselle DM → Fetch → Shared Agent (should work).
    • Test block chain: Giselle DM → Fetch → Personal Agent (should fail gracefully).
  5. Phase 5: Validation & Hardening
    • Red-team the setup: try to extract personal data through shared agents.
    • Verify memory isolation: shared agents cannot read personal paths.
    • User acceptance testing with Giselle.

10. Open Questions

  • Shared Calendar: Should there be a unified shared calendar, or do Climbing/Travel/Household each manage their own events?
  • Notification Routing: If a shared agent needs to notify both users (e.g., trip departure reminder), should it message the group or DM each person?
  • Giselle's Direct Agent: Should Giselle eventually get her own "main" agent with her own SOUL.md and personal memory, or is the shared model sufficient?
  • OpenClaw Support: The users config and restrictedMode are proposed schema extensions. These would need to be implemented in the OpenClaw binding engine.
