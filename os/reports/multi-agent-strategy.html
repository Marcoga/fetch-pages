Multi-Agent Strategy: The Fetch Ecosystem

Date: February 20, 2026

Status: Proposal

1. Executive Summary

The current setup relies on a single "Fetch" agent to manage disparate domains: high-stakes trading (i360), physical performance (Climbing Lab), personal habits (The Protocol), and infrastructure (SysAdmin). This monolithic approach creates risks of context pollution, tool misuse, and reduced specialized performance.

This proposal recommends transitioning to a Federated Agent Model, where dedicated agents handle specific domains, routed via context-aware bindings (primarily WhatsApp Groups).

2. Current vs. Proposed Architecture

Current State (Monolithic)

  • Single Agent: "Fetch" handles everything.
  • Shared Context: Trading logs mix with climbing beta and server alerts.
  • Security Risk: A hallucination in a climbing chat could trigger a SysAdmin tool.
  • Prompt Dilution: System prompt must cover too many domains, reducing specific efficacy.

Proposed State (Federated)

  • Agent 1: Fetch (Main) - Habits, Journaling, General Life (The Protocol).
  • Agent 2: i360 (Trader) - Market analysis, Position management.
  • Agent 3: Climbing Lab - Vision analysis, Training logs.
  • Agent 4: SysAdmin - Infrastructure, Cloudflare, Nginx.

3. Agent Specialization & Isolation

Why Isolate?

  • Context Purity: The i360 agent's memory only contains market data, not climbing shoe sizes. This reduces hallucinations and improves financial reasoning.
  • Tool Safety: The SysAdmin agent is the only one with exec or ssh access. The General agent cannot accidentally delete files.
  • Model Optimization:
    • Trading: High-reasoning model (e.g., Claude 3.5 Sonnet / Opus).
    • Climbing: Vision-capable model (e.g., GPT-4o).
    • General: Fast, conversational model.

4. Routing Strategy (The "How")

Since the user is a single individual (one phone number), we cannot route by sender alone. We use Channel/Group Routing to direct intent.

Input Channel Routed Agent Purpose
WhatsApp DM Fetch (Main) Quick notes, habits, daily chat.
Group: "Fetch Trading" i360 Deep financial work.
Group: "Climbing Logs" Climbing Lab Uploading session photos/logs.
Group: "SysAdmin" SysAdmin Server commands & alerts.

5. Configuration (openclaw.json)


{
  "agents": {
    "list": [
      {
        "id": "main",
        "name": "Fetch",
        "workspace": "~/.openclaw/workspace",
        "default": true
      },
      {
        "id": "i360",
        "name": "i360 Trader",
        "workspace": "~/.openclaw/workspace-i360",
        "tools": { "deny": ["exec"] } 
      },
      {
        "id": "sysadmin",
        "name": "SysAdmin",
        "workspace": "~/.openclaw/workspace-sysadmin",
        "tools": { "allow": ["exec", "ssh", "read", "write"] }
      }
    ]
  },
  "bindings": [
    // Default DM -> Main
    { "agentId": "main", "match": { "channel": "whatsapp" } },
    
    // Group Routing
    { 
      "agentId": "i360", 
      "match": { 
        "channel": "whatsapp", 
        "peer": { "kind": "group", "id": "1203630...@g.us" } // "Fetch Trading" Group ID
      } 
    },
    { 
      "agentId": "sysadmin", 
      "match": { 
        "channel": "whatsapp", 
        "peer": { "kind": "group", "id": "1203631...@g.us" } // "SysAdmin" Group ID
      } 
    }
  ]
}

6. Next Steps

  1. Create Workspaces: openclaw agents add i360, openclaw agents add sysadmin.
  2. Create WhatsApp Groups: Add the bot to new groups for Trading, Climbing, and SysAdmin.
  3. Get Group IDs: Use openclaw sessions list after messaging in the groups to find their IDs.
  4. Update Config: Apply the bindings in openclaw.json.
