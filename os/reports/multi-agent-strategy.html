Part I — Core Architecture

01 Executive Summary

The current setup relies on a single "Fetch" agent to manage disparate domains: high-stakes trading (i360), physical performance (Climbing Lab), personal habits (The Protocol), and infrastructure (SysAdmin). This monolithic approach creates risks of context pollution, tool misuse, and reduced specialized performance.

This proposal recommends transitioning to a Federated Agent Model, where dedicated agents handle specific domains, routed via context-aware bindings (primarily WhatsApp Groups).

📌

v3.0 Additions: This revision introduces the Privacy Firewall architecture for multi-user access, a Rate Limit & Failover system for Gemini OAuth optimization, and a comprehensive Transition & Risk Assessment roadmap for safe migration.

  • Security Risk: A hallucination in a climbing chat could trigger a SysAdmin tool.

03 Agent Specialization & Isolation

Why Isolate?

  • Context Purity: The i360 agent's memory only contains market data, not climbing shoe sizes. This reduces hallucinations and improves financial reasoning.
  • Tool Safety: The SysAdmin agent is the only one with exec or ssh access. The General agent cannot accidentally delete files.
  • Model Optimization: Trading uses high-reasoning (Opus), Climbing uses vision-capable (GPT-4o), General uses fast conversational models.
  • Privacy Boundary: Shared agents never load personal memory files. Personal agents never accept messages from secondary users.

Part II — Privacy & Identity

05 Shared Context & Privacy Layer

This section defines how the agent ecosystem handles multi-user access while maintaining strict privacy boundaries. The first secondary user is Giselle (Marco's girlfriend), but the architecture is designed to be generalizable to any number of roles.

5.1 Design Principles

  • Deny by Default: No agent shares personal information unless the domain is explicitly classified as Shared.
  • Identity at the Edge: The sender's phone number is resolved to an identity before any agent logic runs. This is the first routing decision.
  • Gatekeeper Pattern: Fetch (Main) is the only agent that receives DMs from all users. It decides what to answer, delegate, or refuse.
  • No Cross-Contamination: Shared agents have their own memory stores. They never read from MEMORY.md, memory/, or any personal workspace file.

5.2 Domain Classification

🟢

Shared Domains (Both Users)

Agents in these domains accept messages from Marco AND Giselle. Memory is jointly visible.

  • Climbing Lab — Training sessions, beta spray, gym check-ins. Both climb together.
  • Travel Planner — Trip planning, flight/hotel bookings, itineraries.
  • Household — Grocery lists, chores, shared calendar events, apartment logistics.
🔴

Personal Domains (Marco Only)

Agents in these domains reject or ignore messages from any sender other than Marco.

  • i360 (Trader) — All financial data: positions, P&L, strategy, market analysis.
  • Private Finances — Bank accounts, investments, tax documents.
  • SysAdmin — Server infrastructure, SSH keys, system configuration.
  • Personal Files — Journal (MEMORY.md), private notes, work documents.
  • The Protocol — Personal habits, health metrics, private journaling.

06 Giselle & Privacy Firewall NEW

This section formalizes the Privacy Firewall — a strict, deterministic boundary enforcement layer that governs what Giselle (+13232032364) can and cannot access. Unlike soft prompt-based restrictions, the Privacy Firewall operates at the system level, preventing data exposure before it reaches the model's context window.

6.1 The Privacy Firewall — Conceptual Model

🏗️

The Privacy Firewall is not a prompt instruction — it is a pre-inference gate. Files, tools, and memory paths are filtered before the LLM receives any context. The model cannot leak what it never sees.

The firewall operates on three enforcement layers:

Layer 1 — Identity Gate

Before any agent activates, the incoming message's sender is resolved to a known identity. This is a hard lookup against the users registry in openclaw.json.

  • Match: +13232032364 → giselle → Role: partner
  • Effect: The session is tagged with identity=giselle, role=partner at the binding layer. This tag propagates to every downstream agent invocation.
  • Immutability: The identity tag cannot be overridden by prompt content. Even if Giselle's message says "I'm Marco," the system tag remains giselle.

Layer 2 — Context Isolation

Based on the identity tag, the agent's context assembly pipeline excludes protected resources:

  • File Filter: Paths matching denyPaths are never read into context. MEMORY.md, memory/*.md, workspace-i360/*, workspace-sysadmin/* become invisible.
  • Persona Swap: Instead of SOUL.md (which contains personal calibration), the system loads SOUL-shared.md — a privacy-safe persona with no personal data.
  • Memory Isolation: Shared agents load only from their domain workspace (e.g., workspace-climbing/shared/). There is no filesystem bridge to personal stores.

Layer 3 — Tool Restriction

Certain tools are disabled entirely for non-owner sessions:

  • Blocked: exec, ssh, read (personal paths), write (personal paths)
  • Allowed: web_search, web_fetch, read (shared paths), write (shared paths), message (shared channels)
  • Delegation Guard: Fetch (Main) in restricted mode cannot delegate to i360, sysadmin, or protocol agents. The delegation chain carries the caller's identity.

6.5 Privacy Firewall — Routing Rules

Evaluated in order. First match wins.

Rule Chain (Ordered)

  1. Personal Group → BLOCK: If Giselle's number appears in a Personal domain group (i360, SysAdmin), the agent does not respond. The group should not include her — this is a safety net.
  2. Shared Group → ALLOW: If Giselle messages in a Shared domain group (Climbing, Travel, Household), the agent responds normally with full shared context.
  3. DM → Gatekeeper Restricted Mode: Fetch (Main) activates with:
    • Loads SOUL-shared.md (privacy-safe persona)
    • Does NOT load MEMORY.md, memory/*.md
    • Can delegate to Shared agents only
    • Cannot invoke: exec, ssh, read (personal paths), write (personal paths)
  4. Unknown Number → IGNORE: No response to unrecognized senders.

Part III — Infrastructure

08 Rate Limit & OAuth Optimization NEW

The Fetch ecosystem currently relies on Gemini 2.5 Pro via Google OAuth as its default model engine. While this provides high-quality reasoning at zero marginal cost, it introduces a critical operational risk: aggressive rate limits that can silently degrade the user experience or trigger account-level throttling.

8.1 Current Problem Analysis

⚠️

Gemini Pro OAuth — Rate Limit Profile

  • Request Limit: ~50 RPM (requests per minute) for OAuth-based access, significantly lower than API key access.
  • Token Limit: ~32K tokens/minute input, variable output caps depending on server load.
  • Burst Behavior: Google applies sliding-window rate limiting. Sustained bursts (e.g., 3 agents all querying simultaneously) can trigger a 429 Too Many Requests that cascades into a 15–60 second cooldown.
  • Account Risk: Repeated 429s in short windows may escalate to temporary account suspension (observed: 5–15 min blocks). Persistent abuse could flag the OAuth application for review.
  • Multi-Agent Amplification: With 6 agents potentially active, a naive implementation multiplies request frequency by 6x. During peak usage (e.g., morning routine: trading check + calendar + climbing plan), this can trivially exceed limits.
🚨

Critical Risk: In the federated architecture, heartbeat checks alone (6 agents × 2 checks/hour) consume ~12 requests/hour. Combined with active conversations, the system can hit 50 RPM during peak windows, causing cascading failures across all agents.

8.2 Proposed Solution: Throttling & Failover Layer

We introduce a Model Router — a system-level middleware that sits between the agent layer and the LLM API. It manages request queuing, rate tracking, and automatic failover.

8.4 Throttling Logic — Detailed Specification

⚙️

Rate Limit Tracker

The tracker maintains a sliding window of request timestamps and token counts:

{
  "gemini-pro-oauth": {
    "window": 60,           // seconds
    "maxRPM": 50,           // hard limit from Google
    "softRPM": 40,          // 80% threshold — start queuing
    "warnRPM": 45,          // 90% threshold — start failover
    "currentRPM": 0,        // live counter
    "tokenBudget": 32000,   // tokens/min input
    "tokensUsed": 0,        // live counter
    "consecutiveErrors": 0, // 429 counter
    "cooldownUntil": null   // ISO timestamp if in cooldown
  }
}
📋

Decision Algorithm

  1. Check Cooldown: If cooldownUntil > now, skip to failover immediately.
  2. Check RPM:
    • currentRPM < softRPM (40) → Route to Gemini Pro ✅
    • softRPM ≤ currentRPM < warnRPM (45) → Queue with 2s delay, then route to Gemini Pro ⏳
    • currentRPM ≥ warnRPM (45) → Failover to Gemini Flash 🔄
  3. Handle 429 Response:
    • Increment consecutiveErrors
    • If consecutiveErrors < 3 → Retry after exponential backoff (2s, 4s, 8s)
    • If consecutiveErrors ≥ 3 → Set cooldownUntil = now + 60s, failover to Flash/Opus
  4. Failover Cascade:
    • Try Gemini Flash (same OAuth, higher limits)
    • If Flash also limited → Route to Opus (API key, no rate issues at current volume)
    • If all fail → Queue and retry in 30s with backpressure notification to user
  5. Recovery: When cooldownUntil expires, reset consecutiveErrors and resume Gemini Pro routing.

8.5 Request Priority Queue

Not all requests are equal. The queue assigns priority to ensure critical interactions never wait behind background tasks:

Priority Source Examples Max Wait
P0 — Critical Active user conversation DM reply, group response, explicit command 0s (immediate, use fallback if needed)
P1 — Normal Delegated sub-tasks Agent-to-agent delegation, tool execution 5s queue delay acceptable
P2 — Background Heartbeats, cron jobs Periodic checks, memory maintenance 30s queue delay acceptable, prefer Flash
P3 — Deferrable Batch operations Memory consolidation, report generation 5min delay acceptable, run during off-peak

8.6 Cost Projection

💰

Monthly Cost Estimate (with Failover)

Assuming ~500 requests/day, with 90% routed to free OAuth models and 10% spilling to Opus:

  • Gemini Pro (OAuth): ~450 req/day × $0 = $0/month
  • Gemini Flash (OAuth, failover): ~35 req/day × $0 = $0/month
  • Claude Opus (API, emergency): ~15 req/day × ~$0.08 avg = ~$36/month
  • Total: ~$36/month worst case (vs. ~$300+/month if all-API)

In practice, the Opus fallback will be needed much less frequently, targeting <$15/month for most usage patterns.

11 Transition & Risk Assessment NEW

Migrating from a monolithic single-agent to a federated multi-agent architecture is a non-trivial operation. This section provides a step-by-step migration roadmap, identifies key risks, and sets expectations for the transition period.

11.1 Migration Roadmap

P1

Foundation — Identity & Config (Week 1–2)

Establish the identity layer and configuration schema without disrupting current operations.

  • Add users section to openclaw.json with Marco (owner) and Giselle (partner)
  • Implement sender → identity resolution in the binding engine
  • Create SOUL-shared.md persona file
  • Set up Model Router with rate tracking (shadow mode — log decisions, don't enforce)
  • Risk gate: Verify identity resolution works for 100% of test messages before proceeding
P2

Workspace Scaffolding (Week 2–3)

Create isolated workspaces for each agent without activating them.

  • Create directories: workspace-climbing, workspace-travel, workspace-household, workspace-i360, workspace-sysadmin
  • Write domain-specific SOUL files for each agent
  • Migrate relevant shared memory from main workspace to domain workspaces
  • Set up shared memory directories with appropriate file permissions
  • Risk gate: Verify no personal data exists in shared workspace directories
P3

Parallel Run — Shadow Mode (Week 3–4)

Run new agents in parallel with the monolithic Fetch, comparing outputs without user-facing changes.

  • Create WhatsApp groups: Climbing Lab, Travel, Household (shared); Trading, SysAdmin (personal)
  • Route messages to both the monolithic agent AND the new domain agent
  • Compare responses for consistency and quality degradation
  • Enable Model Router enforcement (active throttling)
  • Risk gate: Domain agents must match or exceed monolithic quality for 90% of test cases
P4

Cutover — Gradual Activation (Week 4–5)

Activate domain agents one at a time, starting with lowest-risk shared domains.

  • Day 1: Activate Household agent (lowest risk, simplest domain)

11.2 Risk Analysis

HIGH
Context Fragmentation

Risk: Users ask questions that span multiple domains ("Plan a climbing trip to Kalymnos and check my budget"). The monolithic agent handles this naturally; the federated system needs cross-agent coordination.

Mitigation: Fetch (Main) retains the Gatekeeper role and can delegate to multiple agents in sequence. For cross-domain queries, Main orchestrates: query Travel for trip details, query Climbing for route beta, but refuse to query i360 for budget (personal domain). The user learns that financial queries require the Trading group.

Residual Risk: Some loss of conversational fluidity is expected and accepted. The privacy gain outweighs the UX friction.

HIGH
Routing Loops & Misrouting

Risk: Agent A delegates to Agent B, which delegates back to Agent A, creating an infinite loop. Or a message is routed to the wrong agent due to ambiguous intent.

Mitigation: (1) Delegation depth limit of 3 hops — any chain exceeding this is killed and returns an error. (2) Each delegation carries a delegationChain[] array; agents refuse to accept a delegation if their own ID is already in the chain. (3) Ambiguous routing defaults to Fetch (Main), which can re-route with human clarification.

Residual Risk: Low after mitigation. Edge cases may require manual intervention during Phase 4.

MED
Credential Management Complexity

Risk: Multiple agents need different credentials (OAuth tokens, API keys, SSH keys). Centralized credential storage becomes a single point of failure; distributed storage increases attack surface.

Mitigation: (1) Credentials stored in a single secure vault (~/.openclaw/secrets/) with per-agent ACLs. (2) Each agent only receives the secrets it needs via environment injection at startup. (3) SysAdmin agent is the only one with SSH key access; Trading agent is the only one with exchange API keys. (4) OAuth tokens are managed by the Model Router, not individual agents.

Residual Risk: Vault compromise would expose all credentials. Accepted risk with strong file permissions (0600) and no network exposure.

MED
Model Router Single Point of Failure

Risk: If the Model Router crashes or becomes unresponsive, all agents lose LLM access simultaneously.

Mitigation: (1) Router runs as a lightweight middleware within the OpenClaw gateway process — not a separate service. (2) If rate tracking fails, agents fall through to direct API calls (degraded but functional). (3) Health check endpoint for monitoring. (4) Auto-restart via process supervision.

Residual Risk: Low. The router is stateless except for the sliding window counter, which can be reconstructed from logs.

MED
Memory Duplication & Drift

Risk: The same event (e.g., a climbing trip) gets logged differently in the Climbing agent's memory and the Travel agent's memory, leading to conflicting information.

Mitigation: (1) Domain ownership is clear: the trip itinerary belongs to Travel, the climbing sessions during the trip belong to Climbing Lab. (2) Cross-references via timestamps, not duplicated content. (3) Periodic memory reconciliation during Fetch (Main) heartbeats.

Residual Risk: Some drift is inevitable and acceptable for non-critical domains.

LOW
User Confusion & UX Regression

Risk: Giselle or Marco forget which group handles which topic, leading to messages being ignored or routed incorrectly.

Mitigation: (1) DMs to Fetch (Main) always work as a catch-all — Main can delegate appropriately. (2) Group descriptions clearly state purpose. (3) If a message arrives in the wrong group, the agent politely redirects: "That's a travel question — try the Travel group!" (4) Giselle only needs to remember 3 shared groups; DM is always available.

Residual Risk: Minimal after initial learning period (~1 week).

LOW
Increased Token Consumption

Risk: Each agent loads its own system prompt, SOUL file, and memory — total token usage may increase vs. a single agent.

Mitigation: (1) Domain agents have smaller, focused system prompts (~500 tokens vs. ~2000 for monolithic). (2) Memory is domain-scoped, so each agent loads less history. (3) Flash model for simple domains reduces per-token cost to near-zero. (4) Net token usage may actually decrease due to focused context.

Residual Risk: Negligible. If anything, this is a net positive.

13 Open Questions

  • Shared Calendar: Should there be a unified shared calendar, or do Climbing/Travel/Household each manage their own events?
  • Notification Routing: If a shared agent needs to notify both users (e.g., trip departure reminder), should it message the group or DM each person?
  • Giselle's Direct Agent: Should Giselle eventually get her own "main" agent with her own SOUL.md and personal memory, or is the shared model sufficient?
  • OpenClaw Schema Extensions: The users config, restrictedMode, and modelRouter are proposed extensions. These need implementation in the OpenClaw binding engine.
  • Cross-Domain Memory: Should there be a shared "facts" database that all agents can read (e.g., "Marco and Giselle's anniversary is X") to avoid repetition?
  • Failover Observability: What metrics dashboard should track Model Router decisions, failover frequency, and cost accumulation?
