🔍 Key Bottlenecks Identified

HIGH IMPACT

1. Serial Data Fetching in beginStart()

The startup chain fetches data sequentially when much of it could run in parallel:

// CURRENT — serial waterfall
env.beginStart()
  → auth.beginStart()          // Auth0 token (NETWORK)
    → config.beginStart()      // Config fetch (NETWORK)
      → api.beginStart()       // API connection
        → accounts.beginStart()  // Account data (NETWORK)
          → contracts.beginStart() // Contract data (NETWORK)
            → orders + trades + watchlists  // ✓ already parallel
              → positions + marketData      // ✓ already parallel

Auth → Config → API must stay serial (dependencies), but accounts and contracts have no dependency on each other and could potentially be parallelized.

HIGH IMPACT

2. Remote Config Fetch Blocks Everything

DomainConfig.applyServiceNgConfig(meson) runs before any service initialization. This is a network call to fetch remote configuration. On slow connections or cold DNS, this alone can add 1-3 seconds.

  • Could the last-known config be cached locally and refreshed in the background?
  • Does the entire config need to be fetched before showing the UI shell?
HIGH IMPACT

3. wireEvents() — Serial Manager Wiring

After prepareWireEvents() (which IS parallel ✓), the actual wireEvents() runs through managers in a serial chain:

env → config → messages → auth → extension → [all others parallel]

The first 5 are serial — if any of them is slow (especially auth.wireEvents() which might hit Auth0), the entire chain stalls.

MEDIUM

4. Loading Animation Gate

Even after all data is ready, the app waits for ART.Core.LoadingAnimationComplete event before transitioning to idle. If the animation has a fixed duration, the UI is artificially delayed. Max timeout: 60 seconds.

// The code waits for animation to finish AFTER service is ready
CoreService._instance?.updateProgress("Service started, awaiting loader sequence completion");
const loadingCompletedPromise = LoadingHandler.getLoadingAnimationCompletedPromise(meson);
void LoadingHandler.publishStartupDone(meson);
MEDIUM

5. 41 Content Windows Bundled as IIFE

Each content window is a separate bundle. On startup, the service content and any initially visible windows (overview, portfolio, etc.) all need to load their JS. If these are large bundles loaded eagerly, it adds to the initial weight.

1 Parallelize beginStart() Data Fetching

Estimated saving: 1-3s

After auth + config + api are ready, fetch accounts, contracts, orders, trades, watchlists, and positions all in parallel:

// PROPOSED — maximum parallelism after API is ready
env.beginStart()
  → auth.beginStart()
    → config.beginStart()
      → api.beginStart()
        → Promise.all([
            accounts.beginStart(),
            contracts.beginStart(),
            orders.beginStart(),
            trades.beginStart(),
            watchlists.beginStart(),
            marketData.beginStart(),
          ])
          → positions.beginStart()  // needs orders + trades
          → activityReport.beginStart()

Risk: Low — need to verify positions/activityReport don't depend on accounts/contracts at init time.

Action: Map dependency graph of all managers' beginStart() methods. Run anything without upstream dependencies in parallel.

QUICK WIN HIGH IMPACT

2 Cache Remote Config Locally

Estimated saving: 0.5-2s

  • On successful config fetch, write to localStorage or Electron's app.getPath('userData')
  • On next launch, use cached config immediately and refresh in background
  • Only block on network if no cache exists (first launch / cache invalidated)

Risk: Medium — stale config could cause issues if server-side config changes (feature flags, API endpoints). Add a config version hash to detect staleness.

3 Shorten or Skip Loading Animation

Estimated saving: 0.5-1.5s

  • If service is ready before animation completes, interrupt it immediately
  • Make animation duration dynamic — shorter for fast connections
  • Consider replacing with a skeleton UI that shows the app layout immediately

Implementation: Check if publishStartupDone could trigger immediate transition instead of waiting for the animation event.

The codebase has built-in lifecycle stats tracking (beginLifecycleOperation, timestamps on each phase). Make this data visible:

5 Parallelize wireEvents() Where Possible

Estimated saving: 0.3-1s

Currently: env → config → messages → auth → extension are serial, then the rest parallel. Check if messages and auth can wire in parallel (they likely don't depend on each other).

6 Lazy-Load Non-Critical Content Windows

Estimated saving: 0.5-2s (initial bundle size)

  • Only load service + overview (or whichever content is the first visible screen) eagerly
  • All other 40 content windows should load on-demand when the user navigates to them
  • Some already use SystemJS (lazy) — ensure all non-critical contents are SystemJS
  • Measure: run --meta build flag to generate esbuild metafiles, then analyze bundle sizes

7 Progressive/Skeleton UI

Estimated saving: Perceived performance improvement

  • Show the app shell (navigation, layout, empty panels) immediately after auth succeeds
  • Fill in data as it arrives (accounts → show account picker, positions → fill portfolio)
  • This changes the question from "when does the loader disappear?" to "when does the user see their data?"

Requires: Decoupling the lifecycle state from data readiness. The UI can be "idle" while data is still streaming in.

8 Electron-Level Optimizations

  • V8 code cache: Enable v8CacheOptions in Electron to cache compiled JS (significant cold start improvement)
  • Preload parallelism: Start loading service content HTML/JS while preload scripts are still executing
  • Window creation: Create BrowserWindow early but show late (avoids white flash)
  • Font loading: RobotoFlex.woff2 is preloaded (good!), but verify it's not render-blocking with font-display: block (currently is — consider swap)
